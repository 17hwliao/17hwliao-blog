> 学习来源：Anthropic Engineering，[The components of agent memory](https://www.anthropic.com/research/components-of-agent-memory)，2026-11-06。本文是读后的个人拆解，实验数字来自原文与官方 cookbook，未在本机复现。

我最初理解的 RAG 很直接：把文档切块，算成向量，提问时召回最相似的几块，再交给模型回答。这条路径解决的是“资料在哪里”，但它没有解决另一个问题：**同一批资料被反复提问时，模型每次都要重新读、重新理解、重新处理冲突。**

Anthropic 在 2026 年 11 月写的《The components of agent memory》，讨论的正是后者。它没有把记忆做成一个更大的向量库，而是把记忆拆成四层，并用一个叫 dreaming 的过程在会话之间整理。这篇笔记按“怎么存、怎么建、怎么查”三个问题拆一遍。

## 一、记忆不是一层，而是四层

原文的图里，一次会话从左边进入，经过 dreaming，再进入下一次会话。中间是四层记忆：

| 层 | 存什么 | 特点 |
| --- | --- | --- |
| Transcripts | 完整会话事件日志，包括工具调用和返回 | 最全、最原始，也是校验记忆的事实来源 |
| Memory notes | 会话中判断“值得记”的观察、规则和踩坑 | 短、可读，但可能错，也可能过时 |
| Memory representations | 从 transcript 和 notes 计算出的结构化表示，例如 wiki | 负责导航和跨文档综合 |
| Injected context | 每次会话自动加载的记忆 | 最贵，必须小，错误会被带进每一次会话 |

这四层的共同点是：**越往上越精炼，越往下越完整。**

最底层是冷存储，保留全量事实；中间是热数据，只记“重新推导很贵”的东西；再往上是索引，负责告诉你“知识在哪里”；最顶层是缓存，只放每次都必须知道的最小集合。

一个很实用的判断标准是：

> 能随时从环境重新读到的事实不要记；记那些不写下来就会永久消失的判断。

## 二、Dreaming：把整理放到会话之外

Dreaming 可以理解为模型的“睡眠期计算”：两次会话之间，模型回看这段经历，把短期经验整理成长期知识。

它主要做五件事：

- **修正错误**：拿记忆去对照原始 transcript，发现记错就改。
- **创建笔记**：从多次会话里提炼共同模式、有效规则和陷阱。
- **构建表示**：增量维护 wiki，合并重复页、补缺失页、修断链。
- **向上提升**：把最稳定、最重要的结论放进 injected context。
- **按目标塑形**：通过“记忆应该为什么服务”的指令，决定哪些信息值得长期保留。

原文里有一个很能说明问题的 Pokémon 实验。Sonnet 3.7 玩了约 1 万步，写了 413 个记忆文件、225 个文件夹，只拿到 1 枚徽章；Fable 5 只写了 9 个文件、2 个文件夹，外加一个 `global.md`，拿到 4 枚徽章。

差别不在“记得多不多”，而在“记什么”。Sonnet 3.7 把屏幕上每回合都能重新读到的位置、金钱、遭遇都记了下来，这些记忆很快过时，还要花时间翻找。Fable 5 记的是策略、计划、验证过的规则，以及游戏不会直接告诉它的东西。

另一个例子是 Mt. Moon。Claude 把 PokéCenter 的位置记错，导致反复走错路。Dreaming 拿着原始 transcript 回查，发现笔记和事实不符，改正后它才走回洞穴并到达下一个城市。

这也是“记忆”与“摘要”的区别：**摘要是把过去压缩成一段话，记忆是让未来还能验证这段话。**

原文还给了两组规模更大的数据：

- 在约 35 万个文件、4.2 亿 token 的内部文档语料上，dreaming 从 2 轮扩展到 128 轮，25 道题的得分从 13% 提升到 48%。
- 当 wiki 和搜索一起使用时，综合得分从 54% 提升到 61%，每题还节省约 2 万 token。

但 wiki 不是在所有任务上都更好。如果答案本来就能从单篇文档里搜到，wiki 的收益不明显；有一个任务里，wiki 甚至长得比原始文档还大，等于画了一张和帝国一样大的地图，失去了抽象的意义。

## 三、Wiki 是怎么建出来的

Wiki 不是一次 prompt 生成的，而是一条多阶段流水线，核心是 **schema 约束 + 并行抽取 + 回读校验 + 全局整理**。

### 1. 先定 schema

在写任何内容之前，先放一个 `_schema.md`，规定目录结构、文件命名、frontmatter 字段、事实格式和链接规则。例如：

```text
entities/<slug>.md      一个实体一个文件
relations/<doc-slug>.md 一份文档里的关系
metrics/<doc-slug>.md   一份文档里的指标
open_questions/<doc-slug>.md 尚未解决的问题
_index.md               全局目录
SKILL.md                怎么读这座 wiki
```

每个文件开头是 YAML frontmatter：

```yaml
---
name: payment-service
description: 支付服务的重试与降级策略
aliases: ["pay-svc", "支付网关"]
metadata:
  type: service
---
```

正文一行一条事实，每条事实末尾带出处：

```markdown
## Current picture
- 当前重试上限 3 次，超限进入死信队列 [source: run-2026-11-12 | as-of: 2026-11-12]

## Failure handling
- 网关超时后重试 3 次，仍失败进入死信队列 [source: run-2026-11-12 | as-of: 2026-11-12]
- 早期版本重试 5 次，因重复扣款降为 3 次 [source: incident-0918 | as-of: 2026-09-18]
```

Schema 的作用不是“好看”，而是让几十个并行 agent 写出来的东西**格式一致、可合并、可检索、可追溯**。

### 2. 并行抽取

把文档按批分给多个 extractor。每个 agent 只读自己那一份，产出实体、关系、指标和未解决问题。

这里有一条关键约束：**单写者规则**。每个 agent 只写自己文档对应的文件，不碰共享文件。否则并发写会互相覆盖。官方 cookbook 也承认，共享页面仍可能丢内容，最繁忙的实体页大约有 5% 的行会被覆盖。

### 3. 补缺口

extractor 遇到文档没写清楚的地方，不猜，而是记成 `open_questions`，或者写一个指向不存在节点的 `[[redlink]]`。resolver 专门处理这些缺口：能查到就补，查不到就标成不可解决，并说明需要哪份文档。

### 4. 回读校验

这是最关键的一步。analyzer 拿着已经写好的记忆，回到原始文档逐条核对：

- 这条事实有依据吗？
- 数字和口径对不对？
- 有没有过时？新值覆盖旧值时，旧值保留为历史。
- 两个文档冲突时，标 `CONFLICT`，不擅自选一个。

所以 wiki 不是“模型摘要的合集”，而是**每条结论都能回溯到原文**。

### 5. 全局整理

最后单独跑一个 organizer，做人类编辑会做的事：合并重复文件、重命名、修复断链、补全 `_index.md`、给风险排序。

一个长节点还会在顶部生成 `## Current picture`，最多 30 行，只放“当前最可能被问到的值 + 冲突/过期记录 + 其他章节索引”。这就是“有损摘要放在入口，无损细节留在下层”。

## 四、没有向量，怎么检索

Wiki 的查询侧没有 embedding，也没有余弦相似度。它让模型拿着工具自己找，走三条通道。

### 通道 1：目录导航

agent 第一步只读 `_index.md` 的前 60 行。这个文件是建库时维护的“地图”，按领域分组，一行一个文件加一句说明。模型根据问题挑一到两个入口。

这相当于**预先做好的语义索引**：不是查询时算相似度，而是建库时就把“什么和什么相关”写下来。

### 通道 2：关键词精确检索

目录里找不到的名字，比如错误码、表名、函数名、配置项，就用 `glob` 找文件名、用 `grep` 搜内容，先列出匹配文件，再决定读哪个。

这一步比向量检索更可靠的地方是：**精确标识符不会被“语义相近”搞混**。`ErrPaymentTimeout` 就是它，不会召回一堆“支付超时”的泛泛段落。

### 通道 3：链接跳转

读到 `payment-service.md`，里面写着依赖 `[[order-db]]`，模型可以顺着链接跳过去。`[[wikilink]]` 就是知识图谱的边。

所以 wiki 的召回其实是：

> 目录（预计算的相关性）+ grep（精确匹配）+ 链接（图扩散）

读的时候也有固定顺序：

1. 先读文件前 60 行，看 `Current picture`。
2. 需要细节再定位到某个 `##` 章节。
3. 只读需要的行，不整篇读。
4. 每条结论带上 `[source | as-of]`。
5. 遇到 `CONFLICT` 就报告冲突，不替用户选。
6. 找不到就明说 `Not in the wiki`，并指出缺哪份文档。

查询侧的 wiki 是**只读挂载**的。原因是：如果查询时允许写，一次猜测就会变成下一位读者的“事实”。要更新，应该走独立的 dreaming 流程。

## 五、和向量 RAG 的边界

| 维度 | 向量 RAG | Wiki 记忆 |
| --- | --- | --- |
| 建库 | 切块 + embedding，分钟级 | LLM 阅读、抽取、校验、整理，小时级 |
| 召回方式 | 相似度 Top-K | 目录 + grep + 链接 |
| 擅长 | 单点事实、模糊语义、长尾问题 | 跨文档综合、重复提问、冲突与版本 |
| 新鲜度 | 重新索引较便宜 | 需要 dreaming 增量维护 |
| 成本位置 | 查询时反复读原文 | 建库时一次性理解，查询时很便宜 |
| 可解释性 | 召回块，较弱 | 每条事实有出处，较强 |
| 失败模式 | 召回不全、块被切断 | 摘要漏信息、并发覆盖、过度抽象 |

官方 cookbook 给了一组成本对照：在 8 份文件、2.8MB 文本的示例上，建 wiki 约 23 分钟、约 16 美元；用 Haiku 从 wiki 回答，得分 91.9，每次约 0.0056 美元；用 Sonnet 直接搜原文，得分 92.8，每次约 0.086 美元。按这个测算，大约问满 240 个问题才回本。

所以 wiki 不是 RAG 的通用替代品。它适合**资料慢变、问题重复、需要跨文档综合**的场景；资料天天变、问题很分散时，向量检索仍然更划算。

更合理的组合是：

- wiki 当索引和预计算层，负责“这堆资料整体在说什么”。
- 原始文档搜索当事实层，负责“这句话到底怎么写”。
- 两者结合，既保留导航，又保留 ground truth。

## 六、对我自己做 Agent 的启发

如果要在自己的项目里落地，我会先做一个最小的三层闭环，而不是一上来就建大 wiki：

```text
memory/
  _index.md          全局目录
  notes/             会话笔记
  entities/          稳定实体
```

工具只需要四个：`glob`、`grep`、`read_file`、`write_file`。

建库时，每份会话记录跑一次抽取，输出固定格式的笔记；再跑一次合并，去重、修链、更新 `_index.md`。查询时，system prompt 固定成“先读索引前 60 行 → 选文件 → 看开头 → 需要再 grep → 顺链接跳 → 引用出处”。

真正难的不是检索，而是三件事：

- **显著性判断**：什么值得记，什么下回合还能重新读到。
- **冲突处理**：两个来源不一致时，保留双方和日期，而不是让模型猜。
- **写入治理**：谁能写、什么时候写、写后怎么校验，避免记忆被一次错误覆盖。

还有两个容易被忽略的风险：

- **记忆会过期**。环境一变，旧规则就可能从资产变成负债，需要定期回读原文。
- **记忆是新的注入面**。如果 transcript 或文档里藏着指令，可能被写进记忆并影响后续会话。原文的 analyzer prompt 明确要求把输入当数据而不是指令，这一点在工程上必须自己实现。

最后用一句话总结这篇原文：

> **RAG 优化的是检索路径，wiki 优化的是知识组织；前者降低查资料的成本，后者降低反复理解的成本。**
