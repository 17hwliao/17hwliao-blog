整理日期：2026 年 10 月 31 日。基础部分关注语言保证，运行时部分会明确区分版本相关的实现。资料以 Go 官方文档、标准库文档和官方博客为主；回答为重新整理的复习笔记，具体项目仍以实际工具链版本为准。

## 一、基础语法与类型（001—010）

### 001. Go 的函数参数是值传递还是引用传递？

**回答：**都是值传递。传入指针时复制的是指针值，传入 slice、map、channel 时也会复制相应的值，但它们可能共享底层数据。因此修改共享数据可能影响调用方，重新给参数赋值通常不会改变调用方变量。

### 002. `new` 和 `make` 的区别是什么？

**回答：**`new(T)` 分配零值并返回 `*T`；`make` 用于初始化 slice、map、channel，返回对应类型的值。比如 `new(map[string]int)` 得到指向 nil map 的指针，仍不能直接写入；`make(map[string]int)` 才得到可写的 map。

### 003. 零值有什么用？

**回答：**变量没有显式初始化时也有确定值：数字为 0、布尔为 false、字符串为空串，指针、slice、map、channel、函数和接口为 nil。零值降低初始化成本，但 nil map 不能写、nil channel 的收发会阻塞，仍需理解每种类型的行为。

### 004. `var` 和 `:=` 如何选择？

**回答：**`var` 可用于包级或函数内，也可只声明类型；`:=` 只能用于函数内的短变量声明。同一作用域的短声明必须至少引入一个非空白的新变量；内层作用域使用 `:=` 还可能遮蔽外层变量，尤其要留意 `err`。

### 005. 常量和变量有什么区别？

**回答：**常量在编译期确定，可以是有类型或无类型常量；无类型常量能在允许的上下文中转换为目标类型，但值必须可表示。变量有运行期存储和值变化。不能把函数调用结果或任意对象都声明成常量。

### 006. `iota` 是什么？

**回答：**`iota` 是常量声明中的计数器，在一组 `const` 声明里从 0 开始，按常量声明项递增，新的一组重新开始。常用于枚举和位标志；公开协议中的编号若要求长期稳定，不能随意在中间插入声明而改变后续数值。

### 007. 类型定义与类型别名的区别是什么？

**回答：**`type UserID int64` 定义一个新的类型；`type UserID = int64` 定义别名，二者是同一类型。新类型适合表达领域语义并约束误用，别名常用于兼容迁移。底层类型相同不等于两个定义类型可以直接互相赋值。

### 008. 为什么 `int` 不能假定永远是 64 位？

**回答：**`int` 的宽度由目标实现决定，常见为 32 或 64 位。数据库 ID、文件格式、网络协议等需要固定宽度时应选 `int64` 等明确类型，并检查转换和溢出；容器长度、索引通常直接使用 `int`。

### 009. Go 包的初始化顺序是什么？

**回答：**先初始化被依赖的包，再初始化当前包的包级变量，随后运行 `init`。同包变量还涉及初始化依赖顺序。不要依靠跨文件的隐含副作用组织业务逻辑；需要配置、错误返回或可控启动顺序的工作更适合放进显式初始化函数。

### 010. 导出标识符与空白导入分别是什么？

**回答：**包级名称以 Unicode 大写字母开头时可被其他包访问。`import _ "某个包"` 只为了触发包初始化，例如注册数据库驱动。空白导入应当有明确目的，避免把重要依赖藏进难以追踪的初始化副作用里。

核对资料：[语言规范](https://go.dev/ref/spec)、[Effective Go](https://go.dev/doc/effective_go)、[Go 代码组织](https://go.dev/doc/code)、[内建函数](https://pkg.go.dev/builtin)。

## 二、字符串、数组与结构体（011—020）

### 011. `string`、`byte`、`rune` 分别表示什么？

**回答：**string 是不可变的字节序列；byte 是 uint8 的别名；rune 是 int32 的别名，常用于表示 Unicode 码点。一个中文字符通常占多个 UTF-8 字节；一个用户眼中的可见字符也可能由多个码点组成。

### 012. `len(s)` 得到的是字符数量吗？

**回答：**对 string 而言得到的是字节数。需要统计 UTF-8 解码后的码点可用 `utf8.RuneCountInString`，但码点数量也不等于字素簇数量。涉及表情组合、变音符号或光标移动时，不能把 rune 直接当作完整可见字符。

### 013. `range` 遍历字符串时拿到什么？

**回答：**索引是当前码点起始位置的字节偏移，值是解码后的 rune。遇到非法 UTF-8 编码时会产生替代码点，并按规则前进。直接 `s[i]` 拿到的是单个字节；因此按字节截断可能切坏中文编码。

### 014. 字符串和字节切片转换会复制吗？

**回答：**从可观察语义上，应当保证修改字节切片不会改变原字符串。编译器可在不改变语义时消除复制，不能把是否分配写死成语言保证。普通业务优先使用安全转换，避免用 unsafe 制造违反不可变约定的共享字符串。

### 015. 大量拼接字符串如何选择实现？

**回答：**少量固定拼接用 `+` 通常清晰；循环累积可考虑 `strings.Builder`，已知大小时适当 `Grow`。Builder 在非零使用后不能复制。是否更快应结合分配次数和基准测试判断，而不是看到 `+` 就一律改写。

### 016. 数组和切片的核心区别是什么？

**回答：**数组长度属于类型的一部分，`[3]int` 与 `[4]int` 是不同类型；数组赋值会复制全部元素。slice 是描述底层数组一段区间的值，长度可变，复制 slice 不会自动深拷贝元素。

### 017. 结构体赋值是深拷贝吗？

**回答：**结构体按字段复制。如果字段是整数、数组等值，会复制相应内容；如果字段包含指针、slice、map，则仍可能共享它们指向的数据。需要独立对象时，应按字段定义复制规则，不能用一次结构体赋值代替任意深拷贝。

### 018. 内存对齐为什么会影响结构体大小？

**回答：**字段按目标平台的对齐规则布局，字段之间以及结构体末尾可能有填充。调整字段顺序有时可减小尺寸，但要用 `unsafe.Sizeof` 等手段在目标平台核实，也要顾及可读性、外部布局约定以及缓存争用。

### 019. 结构体可以比较吗？

**回答：**只有全部字段都可比较，结构体才可用 `==` 比较。包含 slice、map、函数字段的结构体不可直接比较；包含接口字段时，如果动态值不可比较，实际比较仍可能 panic。比较业务对象时通常需要明确哪些字段参与相等判定。

### 020. 结构体嵌入等于面向对象的继承吗？

**回答：**嵌入支持字段和方法提升，是组合机制，没有传统类继承的子类型关系。外层类型不会因此自动变成内层类型；方法名冲突、方法集和接收者规则仍然适用。需要多态时通常通过接口表达行为。

核对资料：[字符串与 Unicode](https://go.dev/blog/strings)、[strings 包](https://pkg.go.dev/strings)、[unicode/utf8 包](https://pkg.go.dev/unicode/utf8)、[unsafe 包](https://pkg.go.dev/unsafe)、[Go FAQ](https://go.dev/doc/faq)。

## 三、切片与共享底层数组（021—030）

### 021. 切片通常包含哪三类信息？

**回答：**可把它理解为底层数组引用、长度和容量。长度决定可索引的范围，容量决定从起始位置到可复用数组末尾的空间。这个模型适合解释行为，但不应依赖未公开的内部布局去做序列化或跨语言传参。

### 022. nil 切片与空切片有什么区别？

**回答：**二者长度都为 0，都可以 range、append。nil 切片可与 nil 比较，非 nil 的空切片不能等同于 nil。对 `encoding/json` 的常规切片编码，nil 通常得到 `null`，非 nil 空切片得到 `[]`，API 返回值需要保持约定。

### 023. `append` 为什么必须接收返回值？

**回答：**append 返回新的切片值，长度会变化，底层数组也可能变化。`s = append(s, x)` 才会更新调用方持有的切片描述；在函数内只改局部参数不会同步外部切片长度，通常应返回更新后的切片。

### 024. append 什么时候影响其他切片？

**回答：**容量足够时可能复用原底层数组，写入会影响共享相同位置的其他切片；容量不足时会分配新数组并复制元素。不能仅凭两个切片变量名称不同，就认为它们拥有独立数据。

```go
package main

import "fmt"

func main() {
	s := []int{1, 2, 3}
	a := s[:1]
	a = append(a, 9)
	fmt.Println(s) // [1 9 3]：仍在复用同一个底层数组
}
```

### 025. 切片扩容总是翻倍吗？

**回答：**不是。增长策略、元素大小、内存分配尺寸以及 Go 版本都会影响最终容量。面试可以解释“小切片与大切片可能采取不同增长策略”，但不要把某个倍率或阈值当成语言契约；应用也不应依赖精确扩容结果。

### 026. 三索引切片 `s[low:high:max]` 有什么用？

**回答：**结果长度为 `high-low`，容量为 `max-low`。例如 `s[:n:n]` 限制剩余容量，追加非零数量元素时就不能继续使用区间之外的旧空间。不过已有元素仍共享底层数组，限制容量不等于完成深拷贝。

### 027. `copy` 能复制多少元素？

**回答：**复制数量是源长度与目标长度的较小值，返回实际复制数量。目标只有容量、长度为 0 时不会复制任何元素；通常先 `make([]T, len(src))` 再 copy。源和目标区间可以重叠，语言定义了安全的复制语义。

### 028. `slices.Clone` 是深拷贝吗？

**回答：**它复制切片元素并获得独立的元素存储，但元素里若有指针、map 或嵌套切片，相应数据仍可能共享。因此它是元素级的浅拷贝；需要递归独立数据时，还要根据元素类型继续复制。

### 029. 删除切片元素后为什么还可能保留对象？

**回答：**缩短长度并不自动清除底层数组里的旧指针，尾部引用可能让对象继续可达。手写删除时需清理不再使用的引用；使用 `slices.Delete` 等库函数时，应核对工具链对应版本的行为，并接收返回的切片。

### 030. 小切片为什么可能占住一大块内存？

**回答：**只要它还引用大数组的一部分，整个底层数组就可能无法回收。长期保留小片段时，可复制到单独分配的切片。缩小 len 或 cap 只限制访问范围，本身不会把旧数组的剩余内存拆开释放。

核对资料：[切片原理](https://go.dev/blog/slices-intro)、[slices 包](https://pkg.go.dev/slices)、[切片删除与引用清理](https://go.dev/blog/generic-slice-functions)。

## 四、map 与数据结构（031—040）

### 031. nil map 能做什么，不能做什么？

**回答：**可以读取、查询长度、遍历和 delete；读取不存在的键得到值类型零值。向 nil map 写入会 panic，写入前需初始化。空的已初始化 map 可以写，因此“长度为 0”不足以判断一个 map 是否可写。

### 032. 如何区分键不存在与值恰好为零值？

**回答：**使用 `v, ok := m[key]`，ok 表示键是否存在。只读取 v 时，两种情况都可能得到零值。业务若允许存储 0、空字符串或 nil，就不能用值是否为空来代替存在性检查。

### 033. 什么类型可以作为 map 的 key？

**回答：**key 类型必须可比较，例如整数、字符串、指针以及字段全部可比较的结构体。slice、map、函数不能作为普通 key。接口可作为 key 类型，但如果放入的动态值不可比较，例如 slice，仍会在运行时 panic。

### 034. map 的遍历顺序稳定吗？

**回答：**不稳定，也不保证每次相同。需要稳定展示、可重现输出或签名输入时，应取出键后按明确规则排序。单元测试直接比较 map 遍历形成的文本，容易产生与业务无关的失败。

### 035. 遍历 map 时可以修改吗？

**回答：**同一 goroutine 中，尚未遍历到的条目被删除后不会再产生；遍历期间新增的条目可能出现，也可能跳过。这个规则不代表支持无同步的并发修改。要求固定快照时应先在锁保护下复制数据。

### 036. map 可以并发读取吗？

**回答：**在正确发布且没有任何并发写入的前提下，可以并发读取。并发读写或多方写入需要同步机制。运行时有时会报并发 map 访问错误，但不能依赖它捕获所有数据竞争；即使没有报错也不说明程序正确。

### 037. 为什么 `m[key].Field = x` 常常编译失败？

**回答：**map 的元素不是可寻址变量，不能直接修改作为值存储的结构体字段。可取出结构体副本、修改后写回；或者存储指针，但指针指向的共享对象仍需独立解决并发访问和生命周期问题。

### 038. map 的容量提示是硬上限吗？

**回答：**不是。`make(map[K]V, n)` 的 n 是初始空间提示，条目可以继续增长。delete 或 clear 移除了内容，也不保证实现立即归还分配空间；需要释放大 map 的存储时，应消除对旧 map 的所有可达引用。

### 039. Go map 的底层永远是“桶加溢出桶”吗？

**回答：**不是。那是常见旧实现的面试模型；Go 1.24 已引入基于 Swiss Tables 的新 map 实现。讨论底层时应先说明版本，再分析哈希、查找、冲突和增长，不能拿旧桶结构解释所有新工具链。

### 040. `maps.Clone` 可以直接解决并发和深拷贝吗？

**回答：**不可以。它提供 map 的浅拷贝，复制时源 map 仍不能被其他 goroutine 无同步地修改；指针、切片等值也仍可能共享内部数据。要做读快照，通常先同步复制，再约定快照中的引用对象是否允许修改。

核对资料：[map 使用与语义](https://go.dev/blog/maps)、[Go 1.24 的 map 更新](https://go.dev/doc/go1.24#runtime)、[Swiss Tables 实现介绍](https://go.dev/blog/swisstable)、[maps 包](https://pkg.go.dev/maps)。

## 五、接口、泛型与反射（041—050）

### 041. Go 如何实现一个接口？

**回答：**通过满足接口的方法集隐式实现，不需要 implements 声明。接口应围绕调用方需要的行为设计，通常保持小而明确；仅为了“以后可能用到”给所有类型设计庞大接口，会增加实现和测试成本。

### 042. 值接收者和指针接收者的方法集有什么区别？

**回答：**类型 T 的方法集包含接收者为 T 的方法；`*T` 的方法集还包含接收者为 `*T` 的方法。可寻址变量的部分方法调用可由编译器自动取地址，但这不意味着 T 在接口赋值时自动拥有 `*T` 的完整方法集。

### 043. 为什么接口中装着 nil 指针，却不等于 nil？

**回答：**接口值携带动态类型和动态值。只有二者都为空时，接口才是 nil；装入 `(*T)(nil)` 后动态类型存在，因此不等于 nil。返回 error 时尤其要避免无意返回带类型的 nil 指针。

```go
package main

import "fmt"

type Problem struct{}

func (*Problem) Error() string { return "problem" }

func main() {
	var p *Problem
	var err error = p
	fmt.Println(p == nil, err == nil) // true false
}
```

### 044. 类型断言和类型转换有什么区别？

**回答：**断言从接口值检查或取出某种动态类型，例如 `v, ok := x.(T)`；转换是把表达式按允许规则变为另一种类型，例如 `int64(n)`。单返回值断言失败会 panic，双返回值断言更适合处理不确定输入。

### 045. `any` 是什么？空接口意味着没有类型吗？

**回答：**any 是 `interface{}` 的别名，能接收任意类型的值，但其中的数据仍有具体动态类型。滥用 any 会把部分检查推迟到运行时；能用具体类型、窄接口或类型参数表达约束时，应优先保持编译期信息。

### 046. 泛型适合解决什么问题？

**回答：**适合不同类型共享同一算法、容器或数据变换逻辑，同时保留类型检查。接口适合表达运行期行为多态。不要为了避免几行重复把业务流程改成难理解的类型参数体系，选择应围绕可读性和实际复用。

### 047. 类型约束中的 `~T` 有什么含义？

**回答：**表示允许底层类型为 T 的类型，例如 `~int` 可接收自定义的 int 底层类型。`int | int64` 表示类型集合的并集。泛型函数只能对所有允许类型都合法的操作进行编译，不能假定具体实例具有额外能力。

### 048. `comparable` 能保证永远不会比较 panic 吗？

**回答：**它约束可比较操作，但要注意接口作为类型实参时的规则。Go 1.20 起，一些接口类型可以满足 comparable 约束；若接口的动态值本身不可比较，比较仍可能 panic。约束检查不能替代对动态数据的约束。

### 049. 反射中的 Type 和 Value 分别负责什么？

**回答：**Type 描述类型信息，Value 表达运行期的值与可执行操作。反射可用于框架、序列化和通用工具，但会增加运行期失败和维护成本。类型明确的业务逻辑优先直接访问或使用接口、泛型。

### 050. 反射修改值为什么常需要传指针？

**回答：**修改要求目标 Value 可设置。`reflect.ValueOf(x)` 常常只拿到副本；传入指针后，经过 Elem 才可能获得可设置目标。还要检查有效性、Kind、nil 与 CanSet，未导出字段也不能随意通过安全反射写入。

核对资料：[Go FAQ 的接口说明](https://go.dev/doc/faq#nil_error)、[泛型教程](https://go.dev/doc/tutorial/generics)、[comparable 的接口规则](https://go.dev/blog/comparable)、[反射三定律](https://go.dev/blog/laws-of-reflection)、[reflect 包](https://pkg.go.dev/reflect)。

## 六、函数、defer 与错误（051—060）

### 051. 闭包捕获的是当时的值，还是变量？

**回答：**闭包可以引用外层变量，后续读取会受到该变量变化的影响。需要固定快照时，可显式复制到新变量或作为函数参数传入。闭包持有引用还可能延长对象生命周期，应留意大对象和并发访问。

### 052. 循环变量被 goroutine 捕获的问题修好了吗？

**回答：**要看语言版本与写法。Go 1.22 新语义下，循环中用 `:=` 声明的迭代变量按迭代独立；使用 `=` 赋给已有变量仍可能共享。模块的 go 版本也参与决定语义，不能对所有代码统一套用新结论。

### 053. defer 何时计算参数，按什么顺序执行？

**回答：**执行 defer 语句时就计算被调用函数及参数，真正调用推迟到当前函数返回时，多次 defer 后进先出。闭包中的变量读取可能发生在退出时，因此 `defer f(x)` 与 `defer func(){ f(x) }()` 的结果可能不同。

```go
package main

import "fmt"

func main() {
	x := 1
	defer fmt.Println("参数快照", x)
	defer func() { fmt.Println("闭包读取", x) }()
	x = 2
}
// 输出顺序：闭包读取 2；参数快照 1
```

### 054. defer 为什么可以修改命名返回值？

**回答：**命名返回值是当前函数的变量。return 设置返回结果后，defer 执行，闭包仍可修改这些变量，再把最终结果交给调用方。这个机制可用于补充错误处理，但过度依赖会让返回值来源难以理解。

### 055. 在大循环中 defer 关闭文件有什么问题？

**回答：**defer 绑定当前函数返回，不是当前一轮循环结束；大量资源可能一直占用到函数退出。可把每轮工作拆进小函数，在小函数中 defer，或者显式及时关闭，并按需求处理关闭失败。

### 056. recover 能捕获其他 goroutine 的 panic 吗？

**回答：**不能。recover 必须在发生 panic 的同一 goroutine 内，由合适的 deferred 函数直接调用才能恢复。需要隔离任务时，应在每个任务边界安排恢复并记录上下文，不能指望主 goroutine 一个 recover 兜住全部任务。

### 057. 所有运行时错误都能 recover 吗？

**回答：**不能。普通 panic 可以在满足条件时恢复，但运行时 fatal throw、资源耗尽的某些情形、`os.Exit` 等不走同一恢复路径。对预期内的业务失败应返回 error，不能把 recover 当作通用容错协议。

### 058. 为什么包装错误用 `%w` 而不是 `%v`？

**回答：**`fmt.Errorf("load user: %w", err)` 保留可解包的错误关系，调用方可继续用 Is、As 判断；`%v` 只是格式化文字。包装时补充有价值的操作上下文，不要在每一层重复同一句话或丢掉原错误。

### 059. `errors.Is` 和 `errors.As` 分别怎么用？

**回答：**Is 检查错误链中是否匹配目标错误，适合哨兵错误；As 查找可赋给目标类型的错误，适合提取结构化信息。不要依赖 Error 文本判断错误种类，也不要只做直接类型断言而忽略外层包装。

### 060. 多个错误应该如何返回？

**回答：**可用 `errors.Join` 合并需要同时保留的错误，例如操作失败与清理失败；Is、As 能遍历其错误树。是否需要合并由接口契约决定，不应为了凑日志把无关错误混在一起，也不要用字符串拼接破坏可判断性。

核对资料：[循环变量新语义](https://go.dev/blog/loopvar-preview)、[defer、panic 与 recover](https://go.dev/blog/defer-panic-and-recover)、[错误包装](https://go.dev/blog/go1.13-errors)、[errors 包](https://pkg.go.dev/errors)、[os.Exit](https://pkg.go.dev/os#Exit)。

## 七、goroutine 与调度（061—070）

### 061. goroutine 和操作系统线程有什么区别？

**回答：**goroutine 是由 Go 运行时调度的执行单元，多个 goroutine 可以复用操作系统线程。线程最终由操作系统调度。goroutine 的创建与栈管理通常较轻，但仍占用内存、调度和应用资源，数量失控同样会拖垮进程。

### 062. GMP 中 G、M、P 各指什么？

**回答：**G 表示 goroutine，M 表示操作系统线程，P 表示执行 Go 代码所需的调度资源。M 需要关联 P 才能执行普通 Go 代码；这是运行时实现模型，不是要求业务程序直接管理的三个对象。

### 063. `GOMAXPROCS` 控制什么？

**回答：**控制可同时执行用户级 Go 代码的处理器资源数量，通常对应 P 的数量，不等于 goroutine 数或进程线程总数。默认值的容器感知和动态更新存在版本差异，调优时要结合实际 CPU 配额及工具链文档。

### 064. work stealing 是什么？

**回答：**当本地可运行任务不足时，调度器可以从其他执行资源的队列中获取工作，改善负载均衡。具体窃取批量、时机和公平性策略属于实现细节，不应通过假定调度顺序来建立业务正确性。

### 065. goroutine 阻塞会把所有任务都卡住吗？

**回答：**不会简单地一概而论。channel、锁等等待通常可挂起当前 goroutine；网络轮询可避免每个连接长期占一个线程。阻塞系统调用、cgo 和 CPU 密集工作各有边界，应分析具体阻塞路径。

### 066. goroutine 调度是完全协作式的吗？

**回答：**现代 Go 具有异步抢占等能力，不只依赖函数主动让出。抢占细节仍受版本、平台和运行状态影响；程序不能把抢占当作同步，也不应使用无限忙循环等待其他 goroutine 修改变量。

### 067. goroutine 栈为什么可以增长？

**回答：**运行时会按需管理栈空间，在需要时扩展，并维护相关指针。初始栈大小和增长机制不是语言常量；回答时重点解释按需使用内存与增长成本，避免把某个固定字节数背成永远不变的保证。

### 068. main 返回后，其他 goroutine 会继续运行吗？

**回答：**不会。main 返回会结束程序，不能保证后台 goroutine 完成，也不能保证它们的 defer 执行。主流程需要使用 WaitGroup、明确的生命周期管理或其他协调机制等待必要工作与资源清理完成。

### 069. goroutine 泄漏通常怎样发生？

**回答：**任务一直阻塞在没有接收者的发送、没有发送者的接收、无法终止的重试或未取消的后台循环上。泄漏的 goroutine 还可能持有大量对象。设计时要明确谁启动、谁取消、阻塞点如何退出以及谁等待结束。

### 070. 如何定位 goroutine 数量持续增长？

**回答：**先观察增长是否与流量或连接数匹配，再对比 goroutine profile 中持续堆积的调用栈，检查 channel、锁、I/O 和取消路径。不要只提高并发上限或定时强制 GC；GC 不会终止仍在等待的 goroutine。

核对资料：[运行时实现说明](https://go.dev/src/runtime/HACKING)、[runtime 包](https://pkg.go.dev/runtime)、[Go 1.25 容器 CPU 感知](https://go.dev/blog/container-aware-gomaxprocs)、[诊断工具](https://go.dev/doc/diagnostics)、[调度器实现](https://go.dev/src/runtime/proc.go)。

## 八、channel 与 select（071—080）

### 071. 无缓冲 channel 与有缓冲 channel 有什么区别？

**回答：**无缓冲收发需要配对完成；有缓冲发送在有空间时可以先进入队列，接收在有数据时可以取出。缓冲区只是有限的解耦，不会让消费者自动变快，也不能替代负载控制与退出协议。

### 072. 对 nil channel 收发和关闭会怎样？

**回答：**发送和接收都会一直阻塞；关闭 nil channel 会 panic。在 select 中把某个 channel 设为 nil 可以禁用对应分支，但需保证还有退出条件，否则可能把整个 select 永久挂住。

### 073. 向已关闭的 channel 发送会怎样？

**回答：**会 panic，重复关闭也会 panic。关闭并不是“拒绝后续发送但不报错”的开关。必须通过所有权和同步协议保证发送已结束后再关闭，而不是先检查一个状态再冒险发送。

### 074. 从已关闭的 channel 接收会怎样？

**回答：**会先取完已有缓冲数据，然后立即返回元素零值；使用 `v, ok := <-ch`，缓冲耗尽且已关闭时 ok 为 false。`for v := range ch` 会在关闭并取空后退出，因此不必另发一个特殊业务值表示结束。

### 075. 谁应该关闭 channel？

**回答：**通常由掌握全部发送结束时机的一方关闭。多个发送者可由协调者等待它们全部退出后统一关闭；接收方不应随意关闭仍有人发送的 channel。channel 也不要求为了回收内存而必须关闭。

### 076. `select` 的多个 case 都就绪时选哪个？

**回答：**语言规定从可执行的通信分支中进行均匀伪随机选择，书写顺序不表示优先级，也不保证业务所需的长期公平。需要强优先级或严格顺序时，应额外设计调度逻辑。

### 077. 为什么 `select` 加 default 可能吃满 CPU？

**回答：**没有通信就绪时 default 立即执行，外层若是无等待的循环，就会持续空转。等待事件应让 select 阻塞，或使用有意义的计时与调度机制，而不是把 default 当作无成本的兜底。

### 078. 关闭的 channel 为什么会让 select 循环空转？

**回答：**关闭并耗尽后的接收一直就绪，循环会反复取零值。如果还要等待其他 channel，识别 `ok == false` 后可把本地 channel 变量设为 nil，禁用分支；如果流程已结束则直接 return。

### 079. `len(ch)` 能用来可靠判断下一次操作不会阻塞吗？

**回答：**不能作为通用同步手段。并发状态可能在读取 len 后立即改变，且无缓冲 channel 的 len 本来就为 0。非阻塞尝试应用 select 的 default 分支表达，真正需要等待时就使用正常收发与取消协议。

### 080. channel、互斥锁应该如何选择？

**回答：**传递任务、结果和所有权时 channel 很自然；保护短小的共享状态时锁往往更直接。选择以状态模型和可理解性为依据。把所有字段读写都绕进 channel，并不会自动减少复杂度或消除死锁。

核对资料：[Go Tour：channel](https://go.dev/tour/concurrency/2)、[缓冲 channel](https://go.dev/tour/concurrency/3)、[关闭与 range](https://go.dev/tour/concurrency/4)、[select](https://go.dev/tour/concurrency/5)、[默认分支](https://go.dev/tour/concurrency/6)、[并发管道](https://go.dev/blog/pipelines)。

## 九、锁、原子操作与内存模型（081—090）

### 081. `sync.Mutex` 的零值能用吗？可以复制吗？

**回答：**零值即可使用；开始使用后不能复制。包含 Mutex 的结构体也应避免按值复制，方法常使用指针接收者。锁保护的是约定的一组状态，所有访问者必须遵守同一约定才有效。

### 082. `RWMutex` 一定比 Mutex 快吗？

**回答：**不一定。读多、临界区足够大且竞争模型合适时可能受益；短临界区和写入较多时，额外管理成本反而可能更高。RLock 期间不能修改共享状态，也不要尝试直接把读锁升级成写锁。

### 083. Go 的互斥锁可重入吗？

**回答：**不可重入。同一调用路径持有锁后再次获取同一把锁可能死锁。避免在锁内调用会回调自身的外部逻辑；多个锁同时使用时应制定一致的获取顺序，并尽量缩短临界区。

### 084. WaitGroup 最常见的使用错误是什么？

**回答：**把正向 Add 放进刚启动的 goroutine，可能让 Wait 先看到 0；应先登记任务再启动，并确保每条退出路径匹配 Done。计数不能为负，使用后不能复制，复用时要等上一轮 Wait 完成。

### 085. `WaitGroup.Go` 是什么？

**回答：**Go 1.25 加入的辅助方法，把启动 goroutine 与任务计数关联起来，函数返回时自动完成计数。文档要求传入函数不能 panic；它也不返回业务错误、不提供取消和并发上限，不能把它当作完整任务调度框架。

### 086. `sync.Once` 中函数 panic 后会重试吗？

**回答：**对 Once.Do 而言，函数 panic 也算已经执行，后续 Do 不会重新调用；递归对同一个 Once 调用 Do 会死锁。需要可重试初始化时，应显式建模状态和错误，不要强行把 Once 当重试器。

### 087. `sync.Map` 能替代全部普通 map 加锁吗？

**回答：**不能。它针对某些访问模式优化，例如条目大多写一次读多次，或不同 goroutine 操作不重叠的键。需要多个键的整体不变量时普通 map 配锁更易控制；Range 也不提供整个 map 的一致快照。

### 088. `sync.Pool` 适合存连接或永久缓存吗？

**回答：**不适合依赖其保存期限。Pool 中的对象可以被运行时随时移除，适合复用可丢弃的临时对象来减少分配。数据库连接应交给连接池管理；缓存需要明确容量、淘汰和失效协议。

### 089. 原子操作能替代多字段事务吗？

**回答：**单次原子操作只保证自身的原子性与相应内存顺序，多个字段组合起来仍可能出现中间状态。可考虑锁、单个不可变快照配原子指针等方案；CAS 循环还需要处理失败重试与对象生命周期。

### 090. 什么是数据竞争和 happens-before？

**回答：**多个 goroutine 无同步访问同一内存位置，且至少一个是写入，就可能构成数据竞争。happens-before 用于表达可证明的先后与可见性关系，可由锁、channel、原子操作等建立；Sleep、日志顺序都不能替代同步。

核对资料：[sync 包](https://pkg.go.dev/sync)、[原子操作](https://pkg.go.dev/sync/atomic)、[Go 内存模型](https://go.dev/ref/mem)、[竞态检测](https://go.dev/doc/articles/race_detector)。

## 十、context 与并发模式（091—100）

### 091. context 主要解决什么问题？

**回答：**在调用链中传递截止时间、取消信号和请求范围的少量值。通常作为函数首个参数显式传递；同一 context 可被多个 goroutine 安全使用。它不是把所有依赖、配置和可选参数都塞进去的通用容器。

### 092. 调用 cancel 就会立即停止 goroutine 吗？

**回答：**不会强杀 goroutine。取消通过 Done 等机制传达信号，任务必须检查或调用支持 context 的 API 才会响应。无法取消的阻塞操作、持续 CPU 计算或忽略错误的重试，可能在取消后继续运行。

### 093. 为什么创建超时 context 后还要调用 cancel？

**回答：**即使设置了超时，任务提前结束后也应调用 cancel，及时释放定时器和父子关联等资源。常见写法是在成功创建后 `defer cancel()`；不能依赖“最终总会超时”来替代及时清理。

### 094. context 应该存进结构体吗？

**回答：**一般按每次调用传入，而不是把请求 context 长期放在服务对象里，否则生命周期容易混淆。真正拥有长期后台任务的组件可显式管理启动与停止，但不能把某次 HTTP 请求的取消状态无意变成全局状态。

### 095. `context.WithValue` 的 key 为什么不推荐直接用字符串？

**回答：**不同包可能使用相同字符串导致冲突，通常定义包内专用的可比较类型作为 key。Value 适合请求 ID 等请求范围信息；数据库连接、必需业务参数和大量数据更适合通过明确参数或依赖传入。

### 096. 如何让 channel 发送可以取消？

**回答：**把发送和 `ctx.Done()` 放进同一个 select，接收侧也考虑取消。若业务发送与取消同时就绪，select 可能选任意可执行分支，因此不能承诺取消发生后绝对不会再发一个值；严格语义需要额外协调。

```go
// 片段：由调用方提供 ctx、out 和 value。
select {
case out <- value:
	// 值已交给下游。
case <-ctx.Done():
	return ctx.Err()
}
```

### 097. worker pool 的核心设计点是什么？

**回答：**限制同时工作的 worker 数，使用有界任务队列，并明确队满时的阻塞、拒绝或丢弃策略。还要处理任务超时、取消、错误收集和关闭顺序。只有固定 worker 数，没有队列边界，仍可能积压到内存耗尽。

### 098. fan-out 与 fan-in 分别是什么？

**回答：**fan-out 把工作分给多个执行者；fan-in 把多个结果来源汇集到一个输出。汇集端只有在所有发送者结束后才能关闭公共结果 channel，并且下游提前退出时要能通知上游停止，避免阻塞泄漏。

### 099. `errgroup` 与 WaitGroup 的区别是什么？

**回答：**WaitGroup 只等待任务结束；`golang.org/x/sync/errgroup` 还能收集首个非 nil 错误，WithContext 可联动取消，SetLimit 可限制活跃任务数。任务仍须主动响应取消，且组返回错误不代表已完成业务补偿。

### 100. 为什么需要背压，而不是无限增加 goroutine？

**回答：**下游的 CPU、连接、内存和请求配额都有上限。背压通过有界队列、并发限制或拒绝策略把容量约束传回上游，避免延迟和内存无限增长。并发限制与每秒请求速率限制不同，通常需要分别考虑。

核对资料：[context 包](https://pkg.go.dev/context)、[context 使用模式](https://go.dev/blog/context)、[context 与结构体](https://go.dev/blog/context-and-structs)、[errgroup](https://pkg.go.dev/golang.org/x/sync/errgroup)、[信号量](https://pkg.go.dev/golang.org/x/sync/semaphore)、[速率限制](https://pkg.go.dev/golang.org/x/time/rate)。

## 十一、内存、逃逸与 GC（101—110）

### 101. 对象一定“局部在栈、返回指针在堆”吗？

**回答：**不能这样判断。编译器结合逃逸分析、内联、对象大小等因素决定存储位置；即使源码出现 new，也不保证一定发生堆分配。应关注可观察语义，再用目标工具链的编译分析与基准确认分配。

### 102. 如何查看逃逸分析？

**回答：**可用 `go build -gcflags='-m=2' ./...` 查看编译器诊断。接口装箱、闭包和跨函数传递有时会影响逃逸，但不能见到某种写法就断言一定逃逸；结合实际输出和 `-benchmem` 才能判断成本。

### 103. 逃逸越少就一定越快吗？

**回答：**不一定。减少堆分配可能降低 GC 压力，但更大的值复制、更复杂的对象复用或锁竞争也会增加成本。优化应比较相同输入下的延迟、吞吐、分配和可维护性，不能只追求某一条编译器诊断消失。

### 104. Go GC 回收对象的基本依据是什么？

**回答：**依据从根对象出发的可达性，而不是引用计数。没有任何可达引用的对象可被回收，因此不可达的循环引用也能回收。仍被全局缓存、goroutine 或大数组间接引用的对象，即使业务不再需要也不会自动消失。

### 105. Go GC 是不是完全没有 STW？

**回答：**不是。Go 将大量 GC 工作与业务并发执行，以降低暂停，但仍存在需要协调的短暂停顿。讨论延迟时要区分并发阶段的 CPU 成本和暂停时间，不能用“并发 GC”推导出“零暂停、零开销”。

### 106. 三色标记与写屏障是什么关系？

**回答：**三色模型帮助解释对象的未访问、待扫描和已扫描状态；并发标记时业务还在改指针，写屏障用于维护正确性，避免遗漏仍然存活的对象。它是理解模型，不能代替对具体版本屏障与扫描实现的核对。

### 107. `GOGC` 调大有什么代价？

**回答：**通常允许堆在两次 GC 之间增长更多，以更高的内存使用换取较低 GC 频率；调小则通常增加 GC CPU 开销。它不是“到固定内存大小就回收”的阈值，也不保证端到端延迟一定随某个方向改善。

### 108. `GOMEMLIMIT` 是硬性 OOM 保护线吗？

**回答：**不是，它是 Go 运行时管理内存的软限制，不能等同于进程 RSS 或容器硬限制，也不能覆盖任意外部内存来源。设得过低可能导致频繁 GC；应结合容器限制、cgo 等额外开销留出空间。

### 109. Go 1.26 的 Green Tea GC 应该怎么回答？

**回答：**Go 1.25 将其作为实验提供，Go 1.26 默认启用。它改进对象扫描等实现以减少 GC 成本，仍应理解为版本相关的运行时优化。不要承诺所有业务都会获得固定比例加速，也不要继续把旧实现细节当作当前唯一实现。

### 110. heap profile 中 `inuse_space` 和 `alloc_space` 有什么区别？

**回答：**前者关注采样时仍在使用的分配字节，适合找保留内存；后者关注累计分配量，适合找分配热点。二者与 RSS 含义不同，也受采样影响；排查泄漏应对比时间序列和引用来源，而不是只看一次峰值。

核对资料：[编译器诊断](https://pkg.go.dev/cmd/compile)、[Go GC 指南](https://go.dev/doc/gc-guide)、[Go GC 的演进](https://go.dev/blog/ismmkeynote)、[Green Tea GC](https://go.dev/blog/greenteagc)、[Go 1.26 更新](https://go.dev/doc/go1.26#runtime)、[pprof 包](https://pkg.go.dev/runtime/pprof)。

## 十二、HTTP、I/O 与资源管理（111—120）

### 111. `http.Client` 应该每次请求都创建吗？

**回答：**通常复用配置好的 Client 和 Transport，利用连接复用并避免反复建连。Client 可并发使用，但配置应在使用前确定，不要边请求边无同步修改。没有总超时不代表绝无阶段超时，仍应按业务明确设置预算。

### 112. HTTP 响应体为什么要关闭？

**回答：**成功获得响应后，调用方需要关闭 Body，防止资源占用。对 HTTP/1.x，读到 EOF 后再关闭通常有利于连接复用；面对未知大小的恶意响应，应采用受限读取，而不是为了复用无限读取整个响应体。

### 113. 请求 context 与 `Client.Timeout` 有什么关系？

**回答：**二者都能约束请求生命周期，通常较早到期的约束先生效。Client.Timeout 覆盖连接、重定向和响应体读取等整体过程；Transport 还有各阶段设置。应先明确总预算，再为连接和响应阶段分配合理限额。

### 114. HTTP handler 启动后台任务需要注意什么？

**回答：**请求返回后，请求 context 可能被取消，不能无意让必须完成的后台工作依赖它继续存活。需要后台任务时应明确转交给有独立生命周期、超时和容量边界的组件，也不能在 handler 返回后继续写 ResponseWriter。

### 115. Go HTTP 服务怎么优雅退出？

**回答：**收到退出信号后停止接受新工作，使用带截止时间的 Server.Shutdown 等待活跃请求结束，并协调业务 worker、连接和缓冲写入。被劫持连接等需要自行管理；超过预算后是否强制关闭要有明确策略。

### 116. HTTP handler 里的 panic 可以只靠业务主函数兜底吗？

**回答：**不可以跨 goroutine 恢复。net/http 对 handler panic 有自身处理，但应用通常仍需在合适的请求边界记录上下文并控制返回策略；不要在已经写出响应后再假装完整返回一个新的正常 JSON 响应。

### 117. `io.Reader` 返回 `n > 0` 且 `err != nil` 时怎么办？

**回答：**先处理已经读到的 n 个字节，再处理错误。一次 Read 不保证填满缓冲，也不保证只在最后一次调用才返回 EOF。需要固定长度数据时可用 `io.ReadFull`，不要把“一次 Read”等同于“收到一条完整消息”。

### 118. `bufio.Scanner` 为什么读长行会失败？

**回答：**Scanner 有 token 大小限制，需要时在扫描前设置 Buffer，结束后检查 Err。特别长的记录也可用 Reader 按协议读取；同时应设置应用允许的最大输入，避免把无限增大缓冲当成安全的解决办法。

### 119. 带缓冲的 Writer 为什么需要 Flush？

**回答：**写入可能只是进入用户态缓冲区，Flush 才尝试把数据交给下层。必须检查 Flush 错误；Flush 也不等于数据已经持久化到磁盘，持久化语义还涉及底层文件 Sync 和实际存储系统。

### 120. 定时器、Ticker 和 `time.After` 有什么注意点？

**回答：**Ticker.Stop 不会关闭它的 C，循环仍需单独退出信号。Go 1.23 起定时器回收与 channel 行为有更新，旧版“未 Stop 必然永久泄漏”的结论不能照搬；高频循环仍要关注重复创建定时器的分配成本和版本兼容。

核对资料：[HTTP 客户端与服务端](https://pkg.go.dev/net/http)、[Reader 契约](https://pkg.go.dev/io#Reader)、[bufio 包](https://pkg.go.dev/bufio)、[文件 Sync](https://pkg.go.dev/os#File.Sync)、[time 包](https://pkg.go.dev/time)、[Go 1.23 定时器更新](https://go.dev/doc/go1.23#timer-changes)。

## 十三、数据库与 JSON（121—130）

### 121. `sql.DB` 是一条数据库连接吗？

**回答：**不是，它是可并发使用的数据库访问句柄，并管理连接池。通常在进程或组件生命周期内复用，不要每个请求都 Open、Close。调用 Open 也未必立即建立有效连接，启动检查可使用带超时的 PingContext。

### 122. 数据库连接池最重要的配置有哪些？

**回答：**关注最大打开连接数、最大空闲连接数、连接最大生命周期与空闲时间。参数需要结合数据库容量、请求并发和中间代理策略设定。上限越大不一定吞吐越高，也可能把数据库推入争用和雪崩。

### 123. 为什么设置连接数上限后出现“像死锁一样”的等待？

**回答：**拿不到连接时调用会等待。如果事务占住连接后，又使用 DB 发起必须等待另一连接的查询，可能形成资源等待。排查应观察 DB.Stats 的等待指标、事务时长和调用链，先修复资源使用，再判断是否调整池大小。

### 124. Query、QueryRow、Exec 如何区分？

**回答：**Query 用于多行结果，QueryRow 用于预期单行并在 Scan 时报告错误，Exec 用于不需要返回行集的操作。具体 SQL 与驱动可能支持 RETURNING 等能力，应按实际结果形式选择，而不是仅按语句名称机械分类。

### 125. 查询多行结果为什么既要 Close，又要检查 Err？

**回答：**Rows 会持有连接等资源，应及时关闭；循环 Next 结束可能表示自然结束，也可能表示迭代出错，因此还需检查 rows.Err。每行 Scan 的错误同样必须处理，不能只检查最初 Query 返回的错误。

### 126. 事务中为什么不能混用 `tx` 和 `db` 执行相关 SQL？

**回答：**tx 绑定事务连接和事务状态，db 可能使用另一连接。混用会让操作跑到事务外，破坏一致性，甚至造成资源等待。事务开始后通常先 defer Rollback，全部成功再 Commit，并单独处理提交失败。

### 127. Go 中如何降低 SQL 注入风险？

**回答：**将值通过参数化查询传递，不拼接未信任输入。占位符形式由驱动决定。表名、列名和排序方向通常不能当普通值绑定，应从固定允许集合映射选择；日志和错误信息也应避免泄露敏感参数。

### 128. JSON 解码到 `any` 时，数字默认是什么类型？

**回答：**使用 encoding/json 时，默认通常解成 float64，大整数可能丢失精度。更稳妥的是定义明确结构体字段；需要通用解码时可用 Decoder.UseNumber，随后按业务范围解析并检查错误。

### 129. JSON 的 `omitempty` 会带来什么坑？

**回答：**零值可能被省略，例如 0、false、空串和空容器；“没有提供”与“明确提供零值”可能因此混淆。可使用指针或显式可空类型表达业务语义，并针对输出契约测试。未导出字段默认也不会作为普通字段编码。

### 130. 为什么解码成功一次不代表整个输入都合法？

**回答：**Decoder.Decode 读取一个 JSON 值后，后面仍可能有第二个值或垃圾内容。要求单一文档时，应继续验证后续为 EOF；对严格 API 还可使用 DisallowUnknownFields，并通过 http.MaxBytesReader 等限制请求大小。

核对资料：[database/sql 包](https://pkg.go.dev/database/sql)、[连接池管理](https://go.dev/doc/database/manage-connections)、[事务执行](https://go.dev/doc/database/execute-transactions)、[防止 SQL 注入](https://go.dev/doc/database/sql-injection)、[JSON 包](https://pkg.go.dev/encoding/json)、[限制 HTTP 请求体](https://pkg.go.dev/net/http#MaxBytesReader)。

## 十四、测试、模块与工程实践（131—140）

### 131. Go 单元测试的基本组织方式是什么？

**回答：**测试放在 `_test.go` 文件中，使用 `func TestXxx(t *testing.T)`。表驱动测试适合表达多组输入与预期，t.Run 可组织独立子测试。既要覆盖正常路径，也要验证边界、错误和资源释放，避免只重复实现代码。

### 132. `t.Parallel` 有什么常见陷阱？

**回答：**并行子测试可能共享变量、目录、全局状态和环境，必须隔离。不要让测试依赖运行顺序；循环变量语义也应结合模块版本判断。改变进程级状态的操作与并行测试存在限制，优先使用 t.TempDir 等隔离资源。

### 133. 如何运行竞态检测？没报错就说明没有竞争吗？

**回答：**常用 `go test -race ./...`。它检测实际执行路径上的数据竞争，会增加运行开销，也受平台支持范围限制。未执行到的路径可能仍有问题，因此没报错不是完整证明，还需要正确的同步设计和有代表性的负载。

### 134. benchmark 应该关注哪些指标？

**回答：**关注 ns/op、B/op、allocs/op，并保证输入、初始化和结果使用符合真实场景。可使用 `go test -bench=. -benchmem ./...`，多次比较避免被噪声误导。Go 1.24 起可使用 b.Loop，旧版本仍常见 b.N 循环。

### 135. fuzz testing 适合发现什么？

**回答：**适合解析器、编解码和输入验证等具有大量边界组合的逻辑，通过种子与输入变异发现崩溃或性质违背。应定义清楚不变量，保留失败样本为回归用例；随机运行没有发现问题不代表证明所有输入安全。

### 136. `go vet`、`gofmt` 和 `govulncheck` 分别做什么？

**回答：**gofmt 统一格式；go vet 检查一些可疑代码模式；govulncheck 结合已知漏洞数据分析项目受影响的调用路径。三者互补，都不能代替业务正确性测试或完整安全审计；工具本身也需要版本管理。

### 137. `go.mod` 与 `go.sum` 分别是什么？

**回答：**go.mod 描述模块路径、go 版本和依赖等要求；go.sum 保存相关下载内容的校验信息，不是传统意义的完整版本锁文件。实际版本选择还取决于模块图，更新依赖时应同时检查改动、兼容性和测试结果。

### 138. 最小版本选择 MVS 中的“最小”是什么意思？

**回答：**对某个模块，选择满足模块图各方要求的最高最低版本需求，而不是把所有依赖自动升级到最新。这样能保留可重现的版本选择。需要升级时应显式操作并验证，不要误以为 tidy 会替你全面升级依赖。

### 139. `go mod tidy` 与 `replace` 有什么边界？

**回答：**tidy 整理构建所需模块和校验记录，不等于升级所有依赖。replace 可替换依赖来源，但主模块的替换配置不会自动成为下游消费者的要求；本地路径替换也不能直接作为可分发依赖方案，提交前要检查。

### 140. 面对“Go 服务变慢了”，如何系统回答？

**回答：**先界定时间窗口、流量变化和受影响指标，再按 CPU、分配/GC、锁等待、goroutine、网络和数据库逐层定位。用 profile、trace 和指标验证假设，小范围修改后对比同条件结果；不要先入为主归因 GC 或盲目加并发。

核对资料：[testing 包](https://pkg.go.dev/testing)、[竞态检测器](https://go.dev/doc/articles/race_detector)、[fuzz 教程](https://go.dev/doc/tutorial/fuzz)、[漏洞管理](https://go.dev/doc/security/vuln/)、[go.mod 参考](https://go.dev/doc/modules/gomod-ref)、[模块与 MVS](https://go.dev/ref/mod#minimal-version-selection)、[go 命令](https://pkg.go.dev/cmd/go)、[诊断指南](https://go.dev/doc/diagnostics)。
